# Modernization & Migration Strategy Case Study

## Executive Summary

This case study documents a 24-month legacy modernization program that decomposed a 15-year-old monolithic Java EE application into a cloud-native microservices platform on Kubernetes. The program delivered measurable improvements in system reliability, deployment velocity, and engineering capacity while maintaining uninterrupted service for over 2 million active users throughout the migration.

---

## Problem Statement

The legacy platform was a Java EE 6 monolith running on JBoss AS 7, deployed to on-premises hardware in a single data center. The application had accumulated 15 years of technical debt across 1.2 million lines of code, with no automated testing, no CI/CD pipeline, and a deployment process that required a 6-hour maintenance window every 8 weeks.

**Critical failure modes:**
- Single data center = single point of failure (99.3% annual uptime; 50+ hours downtime/year)
- 6-hour deployment windows every 8 weeks creating business and customer disruption
- Monolithic database (Oracle 11g, 400+ tables) preventing independent service scaling
- Zero automated test coverage — every release required 2-week manual QA cycle
- Inability to scale individual bottlenecks (checkout service load spiked 40x during promotions)
- Recruitment disadvantage: difficulty attracting engineers to a Java EE / JBoss stack

---

## Modernization Principles

The program was governed by five non-negotiable principles:

1. **Zero big-bang rewrites.** All decomposition happened incrementally using the Strangler Fig pattern.
2. **User experience continuity.** No degradation in end-user functionality or performance during migration.
3. **Measurable progress.** Each phase had defined success criteria before the next phase started.
4. **Engineers migrate their own code.** Product teams owned decomposition of their domains; a dedicated platform team provided the landing zone.
5. **Sunset the old.** Extracted services permanently replaced legacy equivalents — no dual-long-term maintenance.

## Migration Framework

### Strangler Fig Pattern Applied

```
Phase 0                Phase 1                Phase 2               Phase 3
───────────────────────────────────────────────────────────────────────────
                    ┌──────────┐           ┌──────────┐
                    │ New Svc A│           │ New Svc A│
                    └──────────┘           └──────────┘
                         │                     │
┌─────────────────┐  ┌──────────┐  ┌──────────────────┐  ┌──────────────┐
│  Legacy Monolith│  │  Facade  │  │  Facade (reduced)│  │  Decommission│
│  (all traffic)  │─▶│  Router  │─▶│  (legacy shrinks)│─▶│  Legacy      │
└─────────────────┘  └──────────┘  └──────────────────┘  └──────────────┘
```

### Domain Decomposition Strategy

The monolith was decomposed by business domain using Domain-Driven Design (DDD) bounded contexts:

| Domain | Priority | Migration Duration | Data Migration Complexity |
|--------|----------|--------------------|---------------------------|
| Authentication & Identity | P0 | 3 months | Low — isolated schema |
| Product Catalog | P1 | 4 months | Medium — shared references |
| Search & Discovery | P1 | 3 months | Low — read-only replica |
| Checkout & Cart | P2 | 5 months | High — transactional core |
| Order Management | P2 | 4 months | High — complex state machine |
| Inventory | P3 | 3 months | Medium — eventual consistency acceptable |
| Notifications | P3 | 2 months | Low — stateless |
| Reporting & Analytics | P4 | 3 months | Medium — read-path only |

## Database Migration Strategy

Database decomposition was the highest-risk element of the program. The Oracle monolith database was migrated using a three-stage approach:

### Stage 1 — Schema Isolation (Months 1–6)
Identified all tables owned by each bounded context. Enforced schema isolation by removing cross-schema foreign keys and replacing them with application-level lookups. All new code referenced only within-domain tables.

### Stage 2 — Dual Write with Shadow Reads (Months 7–14)
Each extracted service wrote to both the legacy Oracle schema and its new Aurora PostgreSQL database. Shadow reads compared results from both datastores and logged discrepancies for reconciliation.

### Stage 3 — Cutover and Legacy Decommission (Months 15–24)
Once shadow read discrepancy rates dropped below 0.01% per service, the authoritative datastore was switched to Aurora PostgreSQL. Legacy Oracle tables were flagged read-only, monitored for 30 days, and then dropped.

**Data Migration Tooling:**
- AWS Database Migration Service (DMS) for initial bulk load
- Debezium CDC for ongoing replication during cutover window
- Custom reconciliation scripts for data quality validation

## Testing Strategy

Given the zero automated test coverage baseline, the team built a testing foundation alongside the migration:

| Test Layer | Tooling | Coverage Target |
|------------|---------|-----------------|
| Unit tests | JUnit 5, Mockito (Java); pytest (Python) | 80% line coverage per service |
| Integration tests | Testcontainers (per-service DB + Kafka) | All happy paths + top 3 failure modes |
| Contract tests | Pact | All service-to-service API contracts |
| End-to-end tests | Playwright (UI), k6 (load) | Critical user journeys |
| Chaos engineering | AWS Fault Injection Simulator | Quarterly game days |

## Risk Management

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Data loss during DB migration | Medium | Critical | Dual-write + reconciliation; rollback procedure per service |
| Performance regression post-migration | Medium | High | Load testing gates before every cutover; Datadog baselines |
| Feature parity gaps | High | Medium | Acceptance criteria sign-off by Product before decommission |
| Team velocity impact | High | Medium | Dedicated migration squad; feature work paused for migrating teams |
| Oracle license costs during transition | Low | Medium | Negotiated extended license; cost tracked vs. AWS savings |

```
Year 1, Q2  ─── Auth, Search, Notifications extracted
Year 1, Q3  ─── Product Catalog extracted; Oracle schema isolation complete
Year 1, Q4  ─── Checkout & Cart extracted (highest complexity)
Year 2, Q1  ─── Order Management extracted; dual-write validation
Year 2, Q2  ─── Inventory & Analytics extracted
Year 2, Q3  ─── All services on Aurora PostgreSQL; Oracle read-only
Year 2, Q4  ─── Oracle decommissioned; JBoss decommissioned; on-prem retired
```

## Results & Impact

| Metric | Legacy (Baseline) | Modernized | Improvement |
|--------|------------------|------------|-------------|
| Annual uptime | 99.3% (~50 hrs downtime) | 99.97% (~2.6 hrs downtime) | **95% reduction in downtime** |
| Deployment frequency | Once every 8 weeks | Multiple times per day | **40x faster** |
| Deployment window | 6-hour maintenance window | Zero downtime (rolling deploy) | **Eliminated** |
| Mean time to recover | 3.8 hours | 22 minutes | **90% reduction** |
| Lead time for change | 8 weeks | 2 days | **96% reduction** |
| Infrastructure cost | $1.2M/year (on-prem) | $480K/year (AWS) | **60% cost reduction** |
| Checkout page load (P95) | 4.1 seconds | 680ms | **83% faster** |
| Peak traffic capacity | 2x baseline (hard ceiling) | 20x baseline (auto-scale) | **10x capacity increase** |

## Lessons Learned

1. **Database decomposition is the hardest part — start there.** Teams that deferred database migration until late in the project created expensive rework. Schema isolation should begin immediately.
2. **Strangler Fig requires a competent router.** The facade layer that routes between legacy and new services needs its own rigor — bugs there affect all users.
3. **Migration velocity is a product metric.** Treating migration progress as an engineering-internal concern caused stakeholder anxiety. Publishing a public migration dashboard built organizational trust.
4. **Chaos engineering revealed real weaknesses.** FIS game days during Year 2 uncovered a cascading failure mode in the Checkout service that load tests had missed entirely.
5. **Measure the old system while you still can.** Baseline metrics captured in Month 1 were essential for demonstrating ROI at program completion.
